# 水槽ブリッジのメモリ漏れ — 原因と直し方 (2026-08-29 調査)

## 何が起きているか

カメラとブラウザ(水槽画面)をつなぐ橋渡し役 `bridge/aquarium_bridge.py` が、
放っておくと2〜3週間で pi-main のメモリを食い尽くし、店が黙る。
2026-08-21 に「12日間ひとことも喋っていなかった」障害の真犯人。

**今日の実測(2026-08-29)**

| いつ | ブリッジのメモリ |
|---|---|
| 09:42 起動 | (素の状態で 40MB 前後) |
| 17:20 | 288MB |
| 17:35 | 294MB |

**1時間あたり約35MB、1日あたり約800MBのペースで増え続けている。**
毎朝の電源投入でリセットされるので今は表に出ないが、連休などで電源が入りっぱなしになると再発する。

## なぜ漏れるか (実測で名指し済み)

1. カメラは人の位置を **毎秒26回** `zone_state.json` に書き直す。
   書き方は「別名で書いてから置き換える」方式 (`os.replace`)。
2. 橋渡し役はこのファイルの変更を **watchdog** というライブラリの見張り(inotify)で受け取る。
3. **watchdog 6.0.0 に不具合がある。** 「置き換え」の合図は前半(元ファイルが消えた)と
   後半(新ファイルが現れた)の2つで届き、ライブラリは前半を対応表に覚えておく。
   ところが**その対応表から消す処理がどこからも呼ばれない**。
   後片付け用の `clear_move_records()` は定義だけあって呼び出し元がゼロ
   (`inotify_c.py:210`、grep で確認)。
4. 結果、**1日224万件**の合図が積み上がる。

**実証 (pi-main 上で実行)**

    500回 atomic write のあとの記憶件数 = 500     ← 0件のまま増えるだけで一切減らない

**裏取り (本番と同じ条件で二重起動して tracemalloc)**

    +5.1min   watchdog/inotify_c.py:339   7861件 生存
    +10.3min  watchdog/inotify_c.py:339  +8069件 (5.2分で+8069 = 毎秒26件)

計算(26件/秒)と実測(35MB/時)が一致。**ほかに watchdog を使っているプログラムは無い**ので
被害はこの1本だけ。

## 直し方 (推奨): 見張りを頼むのをやめて、自分で見に行く

watchdog を外し、3つのファイル(`zone_state.json` / `aquarium_event.json` / `guest_fish.json`)の
**更新時刻を 50ミリ秒ごとに自分で確かめる**方式にする。変わっていたら今と同じ再評価をし、
変わっていなければ何もしない。

良い点:

- 漏れが**構造的に**消える。ライブラリの不具合に頼らなくなる
- 今は毎秒78回ファイルを読み直しているが、変わった時だけ読むので pi の負担が減る
- 依存ライブラリが1つ減る

気をつける点:

- 反応が最大50ミリ秒遅れる。いちばん敏感なのは口パク開始(`ai_speak_start`)だが、
  音声が実際に鳴り出すまでの遅れの方が桁違いに大きいので体感は変わらない見込み

### 却下した案

- **後片付け関数を自分で定期的に呼ぶ**: 1行で済むが、ライブラリの内部
  (`emitter._inotify._inotify._moved_from_events`)に手を突っ込む形になる。
  watchdog を更新した日に黙って壊れて、また漏れ出す
- **watchdog の更新を待つ**: 6.0.0 が最新で、まだ直っていない

## 段取り

1. Mac で `bridge/aquarium_bridge.py` を書き換え (watchdog → 50ms ポーリング)
2. Mac の stub 環境で4系統を確認 — approach/leave、口パク(ai_speak_start/end)、
   魚の追加・差し替え、接続時の初期同期
3. pi-main へ配って再起動。30分後と翌日にメモリを実測し、横ばいを確認
4. commit & push

## 付随して見つかったこと (今回の範囲外)

- **`zone_state.json` が毎秒26回、SDカードに書き直されている** (1日224万回)。
  この Pi は一度 SD が物理破損している ([[project_uochan_repo_layout]] の 2026-05-20)。
  頻度を落とすか tmpfs に置く価値があるが、カメラと realtime 側に触るので別件
- Mac の aquarium repo に、8/21のテレビ制御の作業 (`tv_guard.py` と `systemd/`) が
  **未コミットのまま**残っている

## 結果 (2026-08-29 実施・commit 98ff676)

| | メモリ | CPU |
|---|---|---|
| 直す前 | 300MB (1時間に35MB増) | コアの約7% |
| 直した後 | **27168KB で25分間 1KBも動かず** | 約1.5% |

- Mac の stub で12件すべて通過。反応の遅れは中央値53ms・最大53ms (口パク開始で20回計測)
- pi-main で通し確認: 本番と同じ書き手で `aquarium_event.json` を speaking→idle と書き、
  **書き込みと同じ秒に `ai_speak_start`**、翌秒に `ai_speak_end` がブリッジのログに出た
- 水槽前の approach/leave の実客での発火はまだ見ていない (店が無人だった)

### 配り方でつまずいた点 (次回のため)

- **`uochan-aquarium` は sudo NOPASSWD の一覧に入っていない** (camera / realtime /
  cam1-infer / admin だけ)。start も restart もパスワードを訊かれる
- しかも `pkill` の SIGTERM は systemd から「正常終了」に見えるので
  **`Restart=on-failure` が拾わず、落としたまま上がってこない**
- 今回は `deploy.sh` と同じ setsid 手動起動でしのいだ。systemd 管理に戻すには
  `pkill -f aquarium_bridge.py; sudo systemctl start uochan-aquarium` を人が打つか、
  次の電源投入を待つ
- 配布は `deploy.sh` を使わずこの1ファイルだけ scp した。deploy.sh は
  `rsync --delete` でツリー丸ごと送るため、pi にしか無いファイル (例 `sound/staff_call.wav`)
  を消す危険がある
